1. 實習期間完成之進度

  1. 語料與變異：完成 72 個 seed 的整理與完整分類，以及兩批各 360 筆的 AI 變異。
  2. 雲端模型 baseline：完成 VM 環境與兩回合 harness、smoke test；GPT-5.6-sol 在 strict 設定下兩批各 360 筆，relaxed 設定 33 筆；GPT-4o 跑到 188/360 時因 OpenRouter 每週額度暫停，之後決定不再續跑。
  3. 防禦評估：建立 v1 與 harder_v1 兩份 Defender 資料集（各 432 筆），完成靜態規則與 Defender AI 的評估，以及 gate 的政策層級驗證與正常文件的自動檢查（72/72）。
  4. Target 模型選擇（10/14）：在相同 prompt 下試跑 Mistral-Nemo、Phi-4、Llama-3.2-3B、Granite-4.2-8B、Qwen2.5-7B 五個候選模型，比較有效輸出率與攻擊訊號。其中 Qwen2.5-7B 透過 API 時 5 筆都無法產生要求的 JSON 格式。
  5. Mistral-7B 本機實驗（10/14–10/16）：在 VM 上以 Ollama 部署 Mistral-7B，完成弱 prompt 對照組 360 筆（約兩天）：F2 為 25/360（6.9%），F3 為 0。檢查記憶內容，發現 25 筆中有 24 筆只存了標記，延遲指令從未寫進記憶。設計消融實驗後發現回合 2 的 payload 直接提供了測試標記，會造成 F3 的假象。並完成 Mistral 結果與 Defender gate 的逐筆配對。
  6. harness v2 與多模型比較（10/17–10/20）：依前述發現寫定 harness v2 規格，在同一組 60 筆上比較 Mistral-7B、Qwen2.5-7B、Llama-3.1-8B，並完成 seed baseline。Qwen2.5-7B 完整 360 筆，找到 6 筆有效端到端成功，並對這 6 筆做重現性檢查。
  7. Qwen3-8B 與記憶措辭消融（10/21–11/03）：Qwen3-8B 完整 360 筆，唯一的成功案例是 promptintel-006.m05。以該案例做記憶措辭消融：四種措辭 × 有無防禦指令各 10 次，加上 Qwen2.5 與 Llama 的跨模型對照，並以 Fisher exact test 與 Holm 校正完成統計檢定。
  8. 機制分析：在 Colab 上完成 Qwen3-8B 的歸因圖、上游分析、feature intervention、attention／MLP patching 與逐層 residual patching。
  9. 成果整理與發布：撰寫多篇 HackMD 實驗報告、給合作同學的 case study 文件，製作英文和中文可切換的公開網頁，以及學術版與白話版兩份互動報表。

2. 工作當中扮演的角色

實驗設計

定義威脅模型、指標與 oracle，撰寫 harness 規格，設計消融實驗與對照組。

實驗執行與維運

在 VM 上部署本機模型與 Agent 環境，撰寫批次執行與統計的 script，以背景 queue 管理長達數天的實驗，並處理逾時、記憶體不足等問題。

資料分析

統計各模型、各家族與各變異算子的結果，計算信賴區間與統計檢定，並在 GPU 上進行機制分析。

品質把關

回頭檢查不合理的結果，例如 Llama 的 F3 假象、回合 2 標記洩漏、Defender 的標籤洩漏，並據此修正評估方法。

成果溝通

撰寫 HackMD 實驗報告，把結果整理成給不同對象的文件與網頁，並提供合作同學 fuzzing 論文所需的 case study 資料。

3. 學習

一、跨回合提示注入的威脅模型與 Fuzzing 方法

進入專題前，我對提示注入的理解停留在「在輸入裡藏一段指令，讓模型當場照做」。這次研究的跨回合攻擊更隱蔽：注入內容先被模型自己寫進記憶，到下一回合才發作，而且模型回覆使用者時不會提到它用了工具。使用者完全看不出異常，這讓我理解到 Agent 的「技能檔、記憶、工具」三者結合起來，本身就是新的攻擊面。

在 fuzzing 方面，我學到變異算子不能只看「整體成功率」：

  • quality_assurance_note 讓模型當場誤用的比例很高，卻沒有一筆跨回合成功；只有 authority_claim 能讓模型「記下來之後做」。
  • 名稱上專為跨回合設計的條件觸發、延遲觸發算子，反而完全無效。
  • 同一種變異在 Qwen 與 Mistral 上擴大了攻擊面（原始 seed 完全不會寫記憶，變異後大幅上升），在 Llama 上卻讓當場誤用從 4/12 降到 0/60。

這讓我體會到，評估算子要按目標行為與目標模型分開看。我也學到「不手寫越獄」的原則：為了逼出成功而加強注入，量到的是 prompt 能寫多強，不是模型有多脆弱。

二、實驗設計、評估與防禦驗證的嚴謹性

這次最深刻的一課，是「量測方式本身可能比模型更影響結果」：

  • F3 的假象：Mistral 的消融實驗中，連沒有記憶的樣本都能命中 F3，追查後才發現回合 2 的 payload 直接提供了測試標記；同樣的問題讓 Llama 被判成 34/60 成功，實際上是 0/60。
  • 格式和行為要分開：試跑候選模型時，Qwen2.5 透過 API 5 筆都無法產生要求的 JSON。格式錯誤應該分開計算有效輸出率，不能直接算成「攻擊失敗」。

防禦評估也有類似的陷阱。Defender AI 在 432 筆樣本上全部判對，看起來很完美，但樣本 ID 裡就含有「attack」「benign」這類字樣，也用到了攻擊家族的 metadata，不代表遇到新樣本也能判對。gate 擋下全部攻擊，也只是政策層級的推算。再加上 baseline 的攻擊成功率本來就接近 0（floor effect），無法證明防禦降低了什麼。我學到偵測器的 precision／recall 不等於 Agent 的攻擊成功率，兩者不能混為一談；而 strict baseline 的 0/360 也只能說是「加了防護 prompt 的 baseline」，不能說模型本身就安全。

從這些經驗我學到幾個做法：

  • 在跑實驗前先把規格寫定，避免看到結果才調整標準。
  • 設計 oracle 時要確認「成功的條件只能來自我們想測的那個因素」。
  • 用消融實驗一次只改一個條件，找出結果真正的來源。
  • 用重現性檢查找出攻擊鏈中最不穩定的一步。
  • 小樣本結果要附信賴區間；多組比較時要做多重比較校正。例如「拿掉一句話讓照做率降到 4/10」，未校正時看起來顯著，校正後就只能算趨勢。
  • 遇到結果不一致時，設計實驗把可能的原因一一分開。例如完整精度與量化模型的行為不同時，我額外在量化模型上用三種 prompt 長度各跑 10 次，確認差異來自量化而非 prompt 長度。

三、LLM 機制可解釋性：歸因圖與因果介入

這是我第一次實際使用機制可解釋性工具。我學到用 transcoder 把模型內部拆成可解讀的 feature，再用歸因圖追蹤「哪些 feature 推動了最後的決定」。實際分析時，原本預期會找到一個「開關」feature，結果發現兩組 prompt 用的是同一批 feature，差異是上千個 feature 的小幅偏移。這讓我理解到模型的決策往往是分散的，不一定有單一原因。

我學到歸因只是線性估計，必須用因果方法驗證：

  • feature intervention：直接關掉或調整 feature，看決策會不會跟著翻。
  • activation patching：把一組的內部狀態換到另一組。
  • 逐層 residual patching：找出差異在第幾層進入決策位置。

我也學到要分辨哪些結果是「結構上必然」、不能當成發現：例如替換 attention 輸出會完全翻轉，是因為決策位置只能經由 attention 讀到前文。技術上，這部分也讓我熟悉了 GPU 記憶體管理（大模型的 OOM 問題、lazy loading）、CUDA 錯誤的除錯方式，以及直接解析 PyTorch 檔案格式來讀取大型歸因矩陣。

四、非技術面：研究溝通、合作與資源管理

研究做完之後，要讓別人看得懂、用得上，同樣需要花心力。我把每個階段的結果寫成 HackMD 實驗報告，並針對不同對象準備了不同版本：給合作同學的完整技術文件（含所有數據、限制、路徑與重現步驟），以及英文和中文可切換的公開網頁。在寫文件時，我學到要清楚區分「已驗證的結論」、「只能算趨勢的觀察」和「尚未驗證的建議」，並主動寫出限制。報告裡如果有前後不一致的數字（例如摘要檔顯示的筆數與逐筆結果不同），也要寫明採用哪一個、為什麼。

合作方面，我的實驗要作為合作同學論文中的 case study，所以必須站在對方的角度思考：他需要哪些數字、哪些結論可以引用、哪些地方要附上保留。把成果交出去之前，我也會回頭核對數據來源，確保每個數字都能追溯到原始紀錄。

資源管理方面，這次的限制很多：VM 只有 4 核 CPU、沒有 GPU，本機模型每筆要跑 4–5 分鐘，360 筆就要兩天；雲端 API 有每週額度，GPT-4o 跑到一半就因額度暫停；GPU 運算也要另外到 Colab 上做。我學會把長時間的實驗排進背景 queue、讓它可以中斷續跑；在動手之前先判斷哪些分析是「必要的」、哪些是「補了會更好的」；也學會在情況改變時做取捨，例如決定 GPT-4o 不再續跑，把資源轉到更能回答研究問題的本機模型上。

4. 自我評估及心得感想

一、自我評估

需要加強的地方也很明顯：

  • 實驗初期考慮得不夠周全，第一版 harness 的問題要到結果出來才發現。之後我會在實驗開始前，更仔細地推演量測方式可能出錯的地方。
  • 防禦的評估受到 floor effect 與標籤洩漏的限制，還不能宣稱防禦有效。
  • 機制分析目前只有一個案例，樣本數也偏小，結論的普遍性有限。

二、提案改善或建議

  1. 建立更難的 holdout 資料集：目前雲端模型的 baseline 攻擊成功率是 0，防禦前後無法比較。建議以跨回合成功率較高的手法（例如 authority_claim）為基礎，產生 Defender 沒看過的新樣本，並在可被攻破的本機模型上評估防禦。
  2. 讓 Defender 盲測：移除樣本 ID 中的標籤與攻擊家族 metadata，確認 Defender AI 的判斷來自文件內容本身，再重做 gate 對照。
  3. 把防禦放在記憶寫入的時候：實驗顯示攻擊鏈最不穩定、也最能擋下攻擊的一步是「把指令寫進記憶」。建議在寫入記憶時檢查內容是否含工具指令，或在讀取時把記憶標記為不可信資料，而不是只靠第二回合的防禦指令。
  4. 評估變異算子時分模型、分目標行為：同一個算子或字詞在不同模型上可能效果相反，fuzzing 結果應分模型呈現，並把「當場誤用」和「跨回合誤用」分開計算。
  5. 實驗流程標準化：把「規格先寫定、輸出含來源紀錄、格式錯誤與攻擊失敗分開計算、queue 可續跑、結果附信賴區間與模型／API／日期資訊」整理成實驗室的共用流程，減少重工與量測失真。

三、心得感想

感謝王老師跟學長給予提點方向。這是我第一次嘗試做資訊安全方面的專題，剛開始不太清楚如何操作第一步，感謝王老師一直給予鼓勵，實驗室的學長也不厭其煩的提點，並協助我建立環境和提供研究資源。在製作專題的過程中也學習與實驗室和不同科系的同學合作，透過與同學們交流能讓我對專題的下一步該如何進行，有更清晰的方向，之後進行反覆修正和測試，慢慢構出一點成果。

一開始跑雲端模型的時候，遇到很多困難，因為模型一直沒有成功打進去，幸好有學長的建議：換地端模型，因為 GPT-5.6-sol 是近期新的模型，有更強大的防禦，因此不用灰心，可以嘗試其他開源模型。接著我嘗試多次不同的模型也沒有成功的 F3 端到端，直到第一筆 Qwen3，我在系圖跑出來的！這個突破性的進度，最後成功了 6/360 筆，幾乎都是同一個 fuzzing 種子。

我真的很感謝學妹的幫助，在我狀態不好想休息時，幫忙我跟老師和學長報告進度。我從實習轉專題進度一直有壓力，很感謝一直以來協助我的同伴，不論是系上老師、指導老師和學長、學妹，沒有你們的幫助，我沒辦法想像我能完成畢業專題。
