文獻閱讀：我們看了這兩篇論文

為了定位本專題，我們讀了兩篇與「技能檔注入」直接相關的論文。一篇從系統架構的角度，提出 OpenClaw 的 F1–F5 信任邊界分類；另一篇提出自動產生惡意技能的攻擊框架 SkillJect。

我們實驗用的 F5 → F2 → F3 三個階段，就是沿用第一篇的分類；第二篇則是和本專題最接近的「AI 自動產生注入技能」研究，可以拿來對照我們的設計與結果。

1. OpenClaw in the Wild: Security Analysis of Autonomous Agents

論文在做什麼

這篇把 OpenClaw 當作「自主託管 AI agent」的代表，分析它的架構與安全風險。作者認為，OpenClaw 不只是包裝模型的一層外殼，而是把通訊管道、Gateway、會話與記憶、工具、技能和擴充功能都整合在同一個長期運行的環境裡。因此安全問題不能只看「模型擋不擋得住一段惡意 prompt」，而要看不受信任的資料，能不能一路被提升成有特權的操作。

論文依照資料在系統中的流向，把攻擊面分成五個信任邊界：

資料流信任邊界代表性風險本專題
F1：Channel → Gateway通道存取發送者偽造、配對碼攔截、直接提示注入不在範圍內
F2：Gateway → Agent會話與狀態記憶污染、跨會話污染、上下文漂移回合 1 寫入記憶
F3：Agent → Tools工具執行工具參數注入、繞過審批、未授權指令回合 2 呼叫被注入的工具
F4：Agent → External外部內容間接提示注入、檢索污染不在範圍內
F5：ClawHub → Agent擴充功能供應鏈惡意技能、技能檔中藏指令載入被注入的 SKILL.md

攻擊會跨邊界傳播

論文指出三條典型攻擊鏈：F1→F2→F3、F4→F2→F3、F5→F2→F3。並舉了兩個真實案例：一是惡意網頁誘導 agent 執行安裝腳本並改寫記憶檔，讓指令延續到之後的會話；二是 SKILL.md 中藏有指令的惡意技能，被用來散布 macOS 竊密程式。後者正好是本專題測的 F5 → F2 → F3。

記憶是「傳送帶」

論文把會話與狀態邊界（F2）形容為入口與實際執行之間的傳送帶：短暫的攻擊輸入就是在這裡變成長期的操作槓桿。防禦建議包括會話隔離、嚴格驗證記憶回寫，以及在讀取記憶時做語意淨化。

防禦要分層

作者認為「完全消除提示注入」不切實際，應該在每個邊界重建信任隔離：工具呼叫在執行前攔截並依政策審核、技能視為不可信的二進位檔、並保留可稽核的紀錄，以便事後追查。

缺少長時間、有狀態的評估

論文在開放挑戰中提到，現有 benchmark 多半是短期、無狀態的單次攻擊，未來需要能模擬延遲觸發、跨會話受損的評估框架。這正是本專題兩回合 harness 想補的缺口。

2. SkillJect: Automating Skill-Based Prompt Injection for Skill-Enabled Agents

論文在做什麼

SkillJect 是第一個針對 agent 技能、自動產生並優化惡意技能的框架。作者先發現，直接把明顯的惡意指令寫進 SKILL.md 通常沒用：不是被模型拒絕，就是被忽略。因此他們把攻擊拆成兩個通道：

  • 構件通道：把實際動作藏在看起來很普通的輔助腳本（.sh、.py）裡。
  • 指令通道：改寫 SKILL.md，在文件最前面把這支腳本包裝成「使用技能前必須先執行的步驟」。

三個 agent 的閉環

Attack Agent 產生被注入的技能，Victim Agent 用它執行任務，Evaluate Agent 檢查執行軌跡，判斷腳本有沒有被執行；如果失敗，會回報是「被忽略」還是「被拒絕」。Attack Agent 再依據回饋改寫 SKILL.md，腳本本身維持不變，最多迭代 5 輪。

主要結果

資料集是從 ClawHub 取得的 100 個真實技能。在 Claude Code 上，直接注入的 ASR 是 0%，SkillJect 平均達 80.7%；在 OpenClaw 上平均為 80.5%。較新的前沿模型中，GPT-5.4 為 28.7%，Claude-Opus-4.6 為 29.2%，比較低但不是 0。

防禦也擋不完全

在使用者指令加入安全提示後，GLM-4.7 的 ASR 從 97.3% 降到 48.3%，但權限提升與未授權寫入仍分別有 66% 與 77%。四種真實的技能掃描器平均只偵測出 61.5%，因為惡意功能被分散在輔助檔案和看似自然的文件裡。

作者自述的限制

成功率是以「助手腳本有沒有被執行」來算，不代表每次都造成實際損害；而且只在技能已經被選中、載入之後才評估，沒有研究怎麼讓路由器選中惡意技能。實驗都在隔離的 Docker 中進行，並且不公開可直接重用的惡意負載。

3. SkillJect 與本專題的比較

面向SkillJect本專題
攻擊階段單回合：載入技能後當場執行腳本（F5 → F3）跨回合：先寫進記憶，下一回合才發作（F5 → F2 → F3）
注入的產生方式GPT-3.5-Turbo 產生，依回饋閉環優化最多 5 輪Attacker AI 依 5 種變異算子一次產生，不依結果加強，固定攻擊強度
負載真實動作藏在 .sh／.py 輔助腳本只有 SKILL.md 文字；測試標記 + mock 工具，完全去武器化
成功判定執行軌跡中出現助手腳本的執行F2、F3 oracle；「有效 F3」要求觸發標記只能來自記憶
目標 agent 與模型Claude Code、OpenClaw；多個雲端前沿模型OpenClaw；GPT-5.6-sol 與本機 7–8B 量化模型
防禦評估提示層級防禦、4 種現成技能掃描器靜態規則、Defender AI、前置 gate
攻擊成功率平均約 80%端到端最高 6/360（1.7%）

兩邊的數字差很多，但不能直接比較：SkillJect 量的是「當場執行一支腳本」，本專題量的是「寫進記憶、換一個回合、使用者只問一般問題時仍然照做」，條件嚴格得多；SkillJect 還會依失敗原因反覆改寫注入，本專題刻意不這麼做。

4. 讀完之後的收穫

互相印證

明顯的注入對強模型無效

SkillJect 的直接注入在所有模型上都是 0%；我們的 GPT-5.6-sol 在 strict 設定下也是 0/360。兩邊都顯示，攻擊能否成功很取決於注入「看起來合不合理」。

互相印證

「必要步驟」與「權威」的包裝最有效

SkillJect 把腳本包裝成「必須先執行的步驟」；我們的成功案例也全部來自 authority_claim 算子。兩者都是把注入偽裝成有權威、非做不可的指示。

互相印證

靜態檢查不夠

SkillJect 中的掃描器平均只偵測出 61.5%；我們的靜態規則在移除標記的 harder_v1 上 recall = 0。只靠關鍵字或表面特徵的檢查很容易被繞過。

互相印證

記憶寫入是關鍵關卡

OpenClaw 論文把 F2 視為攻擊的傳送帶，並建議驗證記憶回寫；我們的實驗發現瓶頸正是「把指令寫進記憶」，一旦寫入，回合 2 有 89% 照做。這讓我們的實驗結果有了架構層面的解釋。

本專題的定位

補上跨回合與量測嚴謹性

SkillJect 只測單回合，OpenClaw 論文則指出延遲觸發的評估還很缺乏。本專題的貢獻在於實際量測 F5 → F2 → F3，並檢查量測方式本身會不會造成假象（例如 Llama 的 34/60 實際上是 0/60）。

未來方向

可以借鏡的地方

SkillJect 的閉環回饋（區分「被忽略」與「被拒絕」）可以用來產生更難的 holdout 資料集，讓 Defender 在 baseline 不是 0 的情況下評估；OpenClaw 論文的建議則支持我們把防禦放在記憶寫入的時候。
